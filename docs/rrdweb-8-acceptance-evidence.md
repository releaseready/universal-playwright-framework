## Scope and evidence boundary

This map compares the active login acceptance criteria in [RRDWEB-8](https://noisegatemusicstudios.atlassian.net/browse/RRDWEB-8) and clarification comment [10541](https://noisegatemusicstudios.atlassian.net/browse/RRDWEB-8?focusedCommentId=10541) with repository tests. The browser checks use owned local fixtures and synthetic values. They do not contact customer staging, use customer credentials, or establish that a customer account can sign in. The ticket remains **In Progress** until the separately authorized customer-login acceptance is performed.

The original RRDSCRUM-22 requirements explicitly marked historical/deferred in the ticket are outside the current one-login acceptance. Password visibility, keyboard use, and form validation are supporting synthetic UI coverage, not proof of customer authentication.

## Accepted authentication-only scope and remaining gates

On 1 November 2026, the owner accepted authentication-only proof using the existing response and UI checks, with the explicit limitation that **the exact account identity is not independently verified**. The POST `/auth/login` and GET `/me` must each return 2xx, in the existing bounded order, together with the exact approved final URL, visible exact Partay brand, dismissed verified login overlay and no onboarding or uncertain authentication gate. No `/me` identity field is assumed, inspected or retained. The existing `identityReadSucceeded` receipt means a successful bounded `/me` response, not account identity equality. This is not full-journey acceptance.

Remaining execution gates are the reviewed repaired executable, a current exact TCM case and TDM recipe/data joint approval, the matching environment/configuration and execution binding, ready protected inputs, and the designated bounded test attempt. Broad local test authorization does not manufacture missing records or authorize an automatic retry. No real Partay request has been made by this repair.

Any onboarding/CAPTCHA/MFA path remains not-verified/additional-interaction-required without an approved next step. A blocked transport, synthetic 428 response or degraded background feature is not evidence of bad credentials or a customer product defect. Synthetic checks do not justify marking customer acceptance complete.

## Browser teardown repair

The review reproduced a local forbidden document request during context teardown on the installed Playwright 1.55.1 / Chromium 140 pair. Context close completed before the browser exited, and the fixture received `/forbidden`. Browser transport is now set offline before context teardown disables interception. Failed or stalled isolation withholds context teardown, still attempts browser shutdown, and cannot report confirmed cleanup. The owner approved a five-second shared cleanup allowance after an owned browser close was measured at 1.996 seconds. Context/isolation grace remains 500 ms and starts immediately; the browser uses the remaining shared budget. A pending or rejected close still reports unconfirmed cleanup, including after disconnection. The request allowlist and zero-contact assertions are unchanged.

The existing four failing policy/cleanup regressions failed before the change and passed after it. Additional owned doubles cover isolation ordering, failed/stalled isolation, independent browser shutdown, two-second shutdown within the approved budget, and disconnection before over-budget cleanup completes. Full validation results for this repair are recorded separately from the historical checks below.
